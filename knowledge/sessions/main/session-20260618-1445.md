## tui-pipeline-reimplementation-plan

The next auwsx pass is a scratch reimplementation of the TUI and a simplifying
refactor of the core model where the model itself creates UI confusion.

Core principle:
- Separate **system truth** from **operator truth**.
- Remove controls that expose implementation plumbing.
- Keep one stable screen with a focus stack instead of page/tab movement.
- If a model word needs repeated explanation, rename the model.

Generalized approach:
1. Identify what the operator is trying to decide at a glance.
2. Split overloaded concepts into independent axes instead of forcing one label
   to carry all meaning.
3. Hide automation internals behind automatic behavior or a single explicit
   operator action.
4. Let context determine actions only when the selected object makes the action
   obvious.
5. Keep detailed internal states only when they drive real scheduler behavior.
6. Refactor domain vocabulary before polishing UI around confusing terms.

## issue-status-target

Issue status should become clearer and progress-oriented.

Target statuses:
- `NEW`
- `PLANNING`
- `PLAN_READY`
- `PLAN_BLOCKED`
- `WORKING`
- `REVIEWING`
- `FIXING`
- `REVIEW_BLOCKED`
- `AUDITING`
- `READY_TO_MERGE`
- `MERGING`
- `RESOLVING_CONFLICT`
- `CONFLICT_BLOCKED`
- `DONE`
- `FAILED`
- `ABANDONED`

Remove or replace:
- `CONSOLIDATING`: project-level routing activity, not issue status.
- `ABSORBED`: backlog routing result / queue-message history, not issue status.
- `NEEDS_FIX`: `FIXING`.
- `ENDED`: `READY_TO_MERGE`.
- `COMPLETING`: `MERGING`.
- `CONFLICTED`: `RESOLVING_CONFLICT`.

Display axes:
- Progress lane for Kanban: `PLAN`, `IN_PROGRESS`, `FINALIZING`, `DONE`.
- Attention marker: idle/running/needs-attention.

Lane mapping:
- `PLAN`: `NEW`, `PLANNING`, `PLAN_READY`, `PLAN_BLOCKED`.
- `IN_PROGRESS`: `WORKING`, `REVIEWING`, `FIXING`, `REVIEW_BLOCKED`,
  `AUDITING`.
- `FINALIZING`: `READY_TO_MERGE`, `MERGING`, `RESOLVING_CONFLICT`,
  `CONFLICT_BLOCKED`.
- `DONE`: `DONE`, `FAILED`, `ABANDONED`.

Needs-attention statuses:
- `PLAN_READY`
- `PLAN_BLOCKED`
- `REVIEW_BLOCKED`
- `READY_TO_MERGE`
- `CONFLICT_BLOCKED`
- `FAILED`

## backlog-routing-and-queue-messages

Approved backlog should route before issue creation or attach to an existing
issue. The routing work is project-agent activity, not an issue phase.

Routing outcomes:
- Standalone: create a new issue at `NEW` or directly `PLANNING`.
- Related to active work: add a queue message to the existing issue and mark the
  backlog item consumed by that issue.

Attachable statuses:
- `PLANNING`
- `WORKING`
- `REVIEWING`
- `FIXING`
- `AUDITING`

Not attachable:
- `PLAN_READY`
- Any blocked status
- Any finalizing status
- Any terminal/archive status

`steering` should be renamed to `queue_messages` or `issue_messages`.
User-facing label: "queue message".

`JOINED`/`ABSORBED` should not be an issue card. Joining is visible through the
backlog item history and the target issue's queue messages.

## routine-output-routing

Routine `type` is too vague. It is currently a fixed enum and mostly becomes
`main_jobs.kind`; it does not clearly describe behavior.

Replace routine `type` with an output routing concept.

Candidate routes:
- `log`: keep result as run artifact/history only.
- `queue`: result may create pending backlog candidates.
- `note`: result may write knowledge/docs within configured writable paths.

UI label should be "Output" or "Routes to", not "Type".

## tui-focus-architecture

The TUI should not be top-level tabs with shared cursors. It needs an explicit
focus stack.

Screens:
- `Main`
- `Settings`

Focus states:
- `LeftNav`
- `ProjectPane`
- `ItemDetail`
- `Settings`
- `Modal`

Project pane focus:
- Kanban
- Archive strip
- Preview

Issue detail sections:
- Detail
- Findings
- Tasks
- Queue messages
- Log

Navigation:
- Left column selects project/item.
- `Enter` enters the right pane.
- In Kanban, `h/l` moves columns and `j/k` moves items.
- Kanban selection updates preview without moving left highlight.
- `Enter` on a Kanban item opens item detail and syncs left selection.
- `Esc` unwinds focus stack.

Only keep:
- Main screen
- Settings screen
- Modal forms/confirmations

Fold old tab content into main/settings:
- Issue view -> right-pane item detail.
- Backlog/routine views -> preview/detail.
- Logs -> issue log section, maybe settings/debug.
- Config -> settings or context project edit.
- Ask -> `?` modal plus optional answer history section.

## keybinding-target

Target keybindings:
- `p`: register new project repository.
- `n`: context new backlog / new routine / queue message on issue.
- `a`: context toggle approve for backlog / toggle routine.
- `?`: ask project.
- `e`: context edit project / backlog / routine.
- `d`: context dismiss/delete/abandon/unregister with confirmation where needed.
- `E`: execute scheduler early now.
- `m`: move mode for project profile movement; moved project appends to target
  profile.
- `S`: global settings screen.

Remove user-facing keys:
- refresh
- triage
- manual issue creation
- manual subtask creation
- separate project config key

## delete-abandon-semantics

Deletion should preserve operator intent and history.

- Backlog `d`: dismiss/remove from live queue; preserve history.
- Routine `d`: delete user routine; disable builtin routine.
- Issue `d`: abandon active work; no effect on `DONE`.
- Project `d`: warn if running work exists; offer cleanup or shallow unregister
  for readdition later.

Backend commands needed:
- project unregister/remove
- routine remove or disable builtin
- issue abandon replacing generic hard remove

## global-settings-and-profiles

Profiles are new persistence, not current project config.

Needed:
- profile table with name/order.
- project belongs to profile and has order within profile.
- moving project to another profile appends it as the last item.
- `S` opens global settings for profiles, Arsenal, default commands, and global
  defaults.
- Context `e` remains project-specific settings.

## Trials & Solutions

- Tried treating `CONSOLIDATING` and `ABSORBED` as issue statuses for UI display
  -> made Kanban and status wording confusing -> reclassify routing/joining as
  project/backlog behavior instead of issue lifecycle.
- Tried a single "big state" for cards -> mixed progress with operator
  attention -> split display into progress lane plus attention/running marker.
- Tried tab-based navigation for issue/backlog/log/config/ask -> caused page
  movement and duplicated context -> move to one main screen with explicit focus
  stack and a separate global Settings screen.
